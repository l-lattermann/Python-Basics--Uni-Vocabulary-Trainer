# 2.2.4 How to integrate custom tools

Course quality: thin — the three code examples are shown but barely explained, and the unit says "the agent can now call `recent_snowfall`" without ever saying that your app must run the function and return its output.
Cards: 9 (basic 6, mc 2, order 1). Additions: 3.
- 02: function calling only *requests* the call; the app runs the function and returns a `function_call_output` with the `call_id`; runs expire after 10 minutes. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/function-calling
- 06: managed identity needs an RBAC role for the Foundry project's identity on the target service (else 401); API keys live in a project connection, one scheme per tool. Source: https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/openapi
- 07: current docs support OpenAPI 3.0 **and 3.1**; `operationId` is required (letters, `-`, `_`). The course text says 3.0 but its own example file declares `"openapi": "3.1.0"`. Source: same OpenAPI page.
- Course code inconsistencies, not carried onto cards: the function calling example uses `create_version(name=...)`, the others `agent_name=...` (docs use `agent_name`, so the code gap 03 does too); the OpenAPI example builds `tool` but passes `tools=[openapi_tool]`.
- Card 09's last step ("the agent calls the function") follows the course wording; card 02's addition gives the precise mechanism.
- Knowledge check 2.2.7 already asks "local function → function calling" and "OpenAPI 3.0 web service → OpenAPI tool", so no scenario mc for those two here; the Azure Functions scenario (04) had no card elsewhere.
- Logic Apps (fourth option in 2.2.3) is not part of this unit and is left to 2.2.3.
