# 1.2.4 Deploy models to endpoints

Course quality: clear, but thin on the deployment types — it lists nine types in one line each, without saying where data at rest lives, what "Developer" limits are, or that the types don't apply to managed compute; "Regional Standard" is not the current product name.
Cards: 15 (basic 11, mc 3, order 1). Additions: 6.
- 1.2.4-01: data at rest stays in the Azure geography for every type; Global/Data Zone/Regional only decides where inference is processed. Source: https://learn.microsoft.com/en-us/azure/foundry/foundry-models/concepts/deployment-types
- 1.2.4-02: provisioned types give lower, more consistent latency; standard types are best effort. Same source.
- 1.2.4-03: batch requests go in one file and use a separate enqueued token quota, so online deployments keep their quota. Same source.
- 1.2.4-04: rename — the docs call "Regional Standard" just **Standard** (SKU `Standard`), processing within an Azure geography rather than strictly one region. Same source.
- 1.2.4-05: Developer deployments live 24 hours, are deleted automatically, and have no SLA or data residency guarantee. Same source.
- 1.2.4-08: deployment types apply only to the serverless API option; managed compute doesn't use them. Same source.
- No plain "Global Standard = general workloads, highest quota" card: knowledge check 1.2.8 Q2 asks exactly that, so its card covers it. Global Standard appears as a distractor in 03.
- Left out on purpose: playground parameters (temperature, top-p, max tokens) and system messages — module 1.5 (optimize model performance) covers them in depth; project vs OpenAI v1 endpoints — module 1.3 unit "Choose an endpoint and SDK" covers them (mentioned only in the explanation of 14).
- The unit shows no code, so there is no code-gap card.
